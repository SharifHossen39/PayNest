- (decision) MVP is one modular Spring Boot monolith with one PostgreSQL database; microservice infrastructure is future-only to preserve learning simplicity.
- (decision) Registration commits User and exactly one zero-balance USD Wallet atomically; failure rolls back both.
- (decision) Transfer locks both Wallet rows in deterministic ID order and uses a non-negative database constraint to prevent overspending and lost updates.
- (decision) MVP persists only COMPLETED Transactions because a failed Transfer rolls back; durable FAILED attempts would require a separate audit mechanism outside scope.
- (assumption) Transfer identifies Recipient by normalized email, avoiding caller use of internal Wallet IDs.
- (assumption) Password validation uses 8-72 characters with no composition rules to keep the learning MVP focused.
- (assumption) Generated BIGINT identifiers are used for simplicity; UUIDs are not required by the product behavior.
- (assumption) Tests and local demos may fund Wallets through non-public fixtures because deposits and public funding APIs are explicitly out of scope.
- (assumption) Transaction participants may see counterpart name and email, while unrelated Users receive no Transaction data.
- (decision) Transaction history is newest-first, zero-based paginated with default size 20 and maximum size 100.
